## The finding that shaped the plan

The frontend ranks on four metrics the regulator does not publish. `scoreUniverse()` in
`src/lib/scoring.js` weights **return, Sharpe, upside capture, downside capture**; the table
also shows max drawdown, holdings count, minimum investment. APMI and SEBI publish returns
and AUM only.

- **Sharpe, max drawdown, volatility** — computable from the monthly `ret_1m` series.
  41 months available; 1,365 approaches have ≥24.
- **Upside/downside capture** — need a benchmark monthly series. `benchmark_return` is
  **empty (0 rows)**: the schema was designed for it, the SEBI parser reads benchmark *names*,
  but nothing ever writes the benchmark's own returns. Gap in the ingest, not just the views.
- **Holdings count, minimum investment** — not published by either source at any frequency.

## Decisions taken
1. **Read path:** Supabase JS client direct from the browser, anon key + read-only views.
   No API server.
2. **Missing fields:** drop holdings and minimum investment; re-weight the composite on
   return, Sharpe and drawdown — all real, all traceable to a filing.
3. **Order of work:** serving layer before backfill. The 37-hour crawl ends with nothing on
   screen; APMI already carries what the leaderboard ranks on.

## Finding: APMI and SEBI never joined — the two sources are disconnected

The detail page surfaced it. Of the 533 leaderboard strategies, **0 have a SEBI row**. Across
the whole latest month: 1,796 APMI approaches, 0 with a benchmark, 0 with a registration
number. Separately there are 1,630 SEBI approaches. The intersection is empty.

Cause: identity resolution is scoped *per source*. `manager_alias` and `approach_alias` both
carry `source` in their keys and every lookup passes it, so a SEBI name never matches an APMI
alias. Each source therefore built its own manager and approach rows:

| source | managers |
|---|---|
| APMI aliases | 421 |
| SEBI aliases | 517 |
| overlap | **0** |

At least 292 manager pairs are the same firm split in two — "Abakkus Asset Manager Private
Limited" exists twice under that *identical* string, as manager 198 and manager 302. 360 ONE,
Alchemy, AlfAccurate, Equirus and ~288 others likewise.

This is not a bug in what was written; the cross-source reconciliation was never built. The
schema anticipated it — `publish_rule.xsource_match_min` (0.95) exists precisely to gate an
"APMI ↔ SEBI approach match" that nothing currently produces.

**Consequence right now:** every SEBI-derived field on the detail page reads "not filed", and
benchmark and registration are blank everywhere. The page handles it honestly, but half the
database is unreachable from the half the site is built on.

## Cross-source reconciliation — built, dry-run clean, NOT YET APPLIED

`ingest/pms_ingest/reconcile.py` + `cli.py reconcile [--apply] [--min-score]`.

Matching is on normalised firm name (`norm_firm`, which strips corporate suffixes), exact
first so a fuzzy near-miss can never steal a SEBI firm that another APMI firm matches
outright. Fuzzy fallback is `difflib` ratio gated at `publish_rule.xsource_match_min` = 0.95,
with a length pre-filter to avoid ~200k full comparisons. **A tie at the top score is parked,
never merged** — the same rule `db.resolve_managers` already follows.

Dry run:

| | |
|---|---|
| matches | **383** (377 exact, 6 fuzzy) |
| ambiguous | **0** |
| APMI managers with no SEBI counterpart | 38 |

All six fuzzy pairs are plainly the same firm: Advisers/Advisors, Managers/Manager,
Holdings/Holding, an `M/S.` prefix, and SEBI's own typo "Managment".

### Merge direction, and why
- **SEBI manager folds into the APMI manager.** The APMI manager survives and inherits the
  registration number, principal/compliance officer and address. Reversed, every
  `approach_id` the site links to would be orphaned.
- **APMI approach survives** where both sources hold the same approach: its id is what the
  leaderboard and `/strategy/:id` already use, and its monthly series is what gets ranked.
- The **benchmark is written onto the surviving tagging row** rather than moving SEBI's
  tagging row, which would collide with the exclusion constraint on
  (`approach_id`, validity range).
- Every pair is recorded in a new `pms.xsource_match` table with its score and method.

### Applied — it worked

Two bugs surfaced on the way, both caught with the database untouched (the whole merge runs in
one transaction, so each failure rolled back cleanly):

1. **Composite FK ordering.** Reparenting an approach must move `approach.manager_id` and the
   denormalised `approach_alias.manager_id` together, and the FK between them rejects *either*
   order while checked per statement. Fixed by making
   `approach_alias_approach_id_manager_id_fkey` `DEFERRABLE` and deferring it for the merge.
   The guarantee is unchanged — a transaction leaving the two disagreeing still fails, at commit.
2. **`sebi_reg_no` is unique** and the losing row still held it when the survivor claimed it.
   Released first.

## Benchmark return series

APMI is not a source for this — its `benchmark` fields are form inputs, not data. SEBI is the
only one, and its parser already *read* the benchmark rows beside every approach; it used them
only to tell SEBI's 0-as-null apart from a real zero, then threw the numbers away.

- `sebi.py` — new `BenchmarkReturn`, collected per filing and deduped by `benchmark_norm`.
  **`ret_si` is deliberately excluded**: for a benchmark, SEBI computes since-inception from
  the *approach's* inception date, so the same index carries a different `ret_si` on every
  approach it benchmarks. It is an approach-level number wearing an index's name.
- Two approaches quoting different figures for the same index in the same month are recorded
  as `benchmark_conflicts` on the filing, never averaged.
- `db.upsert_benchmark_returns` — first writer wins; a later filing only fills windows the
  first left null, never overwrites.
- `public.v_benchmark_return`, and `v_strategy` gains `bench_ret_1y/3y/5y` and
  `excess_1y/3y/5y`. StrategyDetail now shows a three-row table: strategy, benchmark,
  difference — dated separately, because SEBI lags APMI by a month.

From three benchmarks alone, **247 strategies already carry a real excess-return figure.**

### Bug found and fixed: phantom revisions
Test re-running one manager logged **138 revisions on identical data** — `0.4200` → `0.42`,
`8.7089` → `8.7089`.

`upsert_sebi_approach_monthly` and `upsert_sebi_manager_monthly` both did
`float(o) if isinstance(o, (int, float)) else o`. Postgres returns `numeric` as **Decimal**,
which is not an instance of either, so the cast never fired and every numeric column compared
Decimal against float. `upsert_apmi` was already correct — it casts unconditionally — so only
the SEBI paths were affected.

Replaced with a shared `_same()` that compares numerically with a 1e-9 tolerance and handles
bools and None explicitly; unit-checked against Decimal/float/bool/None cases. Deleted 194
provably-phantom rows (old and new numerically identical) — 138 from the test, 56 pre-existing.
`fact_revision` is now 332 real restatements.

Left unfixed, this would have written ~90k junk rows into the audit trail on the full re-run.

## Fees — made a real calculator rather than a claim

The maths here was already sound and the page already listed what it ignored. Three real
problems remained:

1. **The rates were fixed**, so you could not price the offer actually in front of you.
2. **GST was hand-waved** — "brokerage, GST at 18%, custody and exit load add roughly 0.3–0.6
   points". GST is statutory and exactly knowable; it belongs in the arithmetic, not in a
   footnote. At ₹1 cr flat fee it is ₹45,000 on a ₹2,50,000 fee, which is not a rounding note.
3. **Nothing said the rates were not real.** Every other number on this site is a filed figure;
   these are the only invented ones on the whole site now, and they were not labelled as such.

Changes:
- `src/data/fee-defaults.js` — defaults, with the provenance stated at the top of the file:
  neither SEBI nor APMI publishes what a manager charges.
- `src/lib/fees.js` — GST included in the total and shown as its own line; new
  `crossoverPoint()` solves for the gross return at which the ranking flips.
- Every rate (fixed / share / hurdle) is now an input. Reset returns to the defaults.
- A panel at the top of the page says plainly where the rates come from: *nowhere*.
- **Modelling convention made explicit and switchable.** The performance share is charged on
  the gross gain above the hurdle with the fixed fee billed separately; some agreements take
  the share on the gain *net* of the fixed fee, which is cheaper for the investor. Agreements
  genuinely differ and the old code silently picked one.

Verified: GST ratio exactly 1.18; at ₹1 cr the crossover is **20.5% gross** — below it
profit-only is cheapest, above it flat fee wins. The page's headline ("a profit-only fee is not
always the cheap one") is now demonstrated by its own calculator rather than asserted.

`FEE_MODELS` / `FEE_AMOUNTS` in `data/content.js` are now unused by `src/`.

The Decimal-vs-float fix earlier was correct but incomplete. The re-run logged **4,942 fresh
revisions** — all real differences, all meaningless:

```
aum_cr_total   706.24  ->  706.24244
ret_3y          12.81  ->   12.81004
```

`*_cr` columns are `numeric(16,2)` and `ret_*` are `numeric(9,4)`, so Postgres rounds on write.
Comparing the stored value against the freshly parsed one at full precision reports a revision
on every money column of every re-run, forever, making the "revised" counter meaningless and
burying genuine restatements.

`_same()` now takes the column's scale and compares at it. The scale is read from
`information_schema` and cached (`column_scales`) rather than hardcoded, so changing a column
type cannot silently reintroduce this. Applied to all three upserts — APMI's hand-rolled
comparison had the same flaw.

Deleted 4,897 rounding artefacts. `fact_revision` is **377**, and what remains is genuine: APMI
return restatements, 35 approaches across every window.

Verified: re-running the same manager now reports `0 revised` and writes no rows. The identical
command logged 138 earlier today.

## Firm logos

Neither source publishes a logo, so the problem was finding a domain per firm. The SEBI filing
turns out to carry one: the identity table includes *Email ID of the Principal Officer* and
*of the Compliance Officer*. `ravi@valuequest.in` gives `valuequest.in`.

Derived from the 649 raw snapshots already on disk — **no re-fetch**. 378 usable company
domains (generic providers like gmail/rediffmail discarded), covering 1,122 of 1,796
strategies.

**PRIVACY:** only the derived domain is stored. The email addresses are named individuals'
work contacts; SEBI listing them on its own register is not the same act as republishing them
on a marketplace, and the domain is all that is needed.

- `ingest/scripts_domains.py` — parses raw filings, fills `manager.website_domain`.
- `ingest/scripts_logos.py` — fetches each icon **once** into `public/logos/`. Deliberately not
  hot-linked at render time: that would send every viewer's page loads, and which firms they
  browse, to a third party, and would break the page whenever that service changed. Two
  sources tried in order (Google, then DuckDuckGo — the latter succeeds on sites Google
  returns nothing for). Any payload repeating across 5+ unrelated domains is treated as the
  placeholder globe and dropped.
- `src/data/logo-domains.js` — **generated manifest**. Without it the app renders an `<img>`
  for every firm, and Vite answers a missing file with `index.html` at HTTP 200, so each miss
  quietly downloads the whole page as a would-be image. The fetch script regenerates it.
- `FirmMark` takes a `domain`, renders the logo when the manifest has it, and falls back to the
  existing geometric mark otherwise — including on a render-time decode failure.

**280 logos, 1.2 MB.** 277 distinct images; the three repeats are affiliated firms sharing a
mark (`sparkcapital.in` / `sparkfund.in`). Covers 860 strategies and 143 of 297 ranked firms.

### Regression caught: ALL CAPS firm names
**190 of 556 display names had gone to block capitals**, e.g. "Enam Asset Management Company
Private Limited" → "ENAM ASSET MANAGEMENT CO.PVT.LTD".

Caused by the cross-source merge. SEBI files in capitals and abbreviates; APMI files mixed
case and in full. Before the merge these lived on separate manager rows and never met —
afterwards `resolve_manager_by_regno` did a plain last-writer-wins `update manager set name=…`,
so the July re-fetch let SEBI overwrite every merged firm's name. Only noticed because logos
put firm names under close reading.

Fixed at both ends: new `better_display_name()` prefers a name containing lowercase, then the
fuller spelling, so it cannot recur; and the existing rows were repaired — 137 corrected, 79
still capitalised because no better alias exists anywhere.

The repair first failed with `server closed the connection unexpectedly`: 556 individual
updates held one connection past the pooler's limit, the exact failure `connect_short` was
written for. Redone as a single `update … from (select distinct on …)`.
